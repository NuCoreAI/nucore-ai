# Tool cardinality inventory

Audit of every tool in `src/unified/tools/*.json` (34 files) for one question: does one call act on
or read multiple objects, or exactly one — and does the tool's own `description` say anything about
that cardinality at all.

Background: `send_command` used to accept exactly one device+command per call; it's been changed to
accept a `commands` list (see `src/unified/tools/tool_device_send_command.json` and
`src/unified/handlers/command_control_status.py`). While looking at routines, the same
one-object-per-call limitation turned up in `routine_status_op`, which prompted this full audit.
Following that, `NUCORE ASSISTANT`/`CRITICAL RULES` were trimmed to stop stating a generic,
tool-agnostic cardinality rule, and seven tools (`routine_status_op`, `node_op`, `variable_op`,
`group_scene_op`, `plugin_ops`, `get_property`, `get_device_family`) had their own description
edited to state their single-object cardinality directly. Most recently, `get_property` itself was
made multi (a list of `{device_id, property}` entries, not a cross-product -- see its row below for
why that distinction matters), and `group_scene_op` lost its `add_member` operation entirely (fully
redundant with `multi_device_scene`, which now handles every add) -- the "Full description
(verbatim)" column below reflects all of that.

Interactive version (filterable, with counts, full descriptions rendered with real paragraph/code
formatting): https://claude.ai/artifact/8sznfvbNA9WkrWnT71rqtn

## Key takeaways

- **Same structural gap as `routine_status_op`, silent on cardinality in the sense that mattered
  (no list-capable layer at all)**: `node_op`, `variable_op`, `group_scene_op`, `plugin_ops`,
  `get_device_family`. A customer asking to enable/disable/delete several routines, rename several
  nodes, update several variables, remove/update several scene-member links, or check several
  devices' protocol family in one turn forces N separate tool calls today. All five now at least
  state their own cardinality directly in their description (see the table above), even though the
  underlying single-object limitation itself is unchanged.
- **`get_property` — fixed, not just documented.** Previously in the list above; now takes a
  `properties` list of `{device_id, property}` entries. Several properties on the *same* device
  were already free before this fix (the interface's `get_properties(device_id)` call always
  returned every property for that device — the old handler just discarded all but one), so this
  mainly buys batching *across* devices, parallelized rather than one call per turn.
- **`group_scene_op` lost `add_member`.** It was fully redundant with `multi_device_scene` (the
  same underlying `group_scene_add_member` call, even for one device) except that it skipped the
  role precheck and controller-conflict guard `multi_device_scene` runs. `group_scene_op` is now
  `remove_member`/`update_link` only; every add goes through `multi_device_scene`.
- **Already multi, but only at the handler level, not the interface**: `get_routine_details`,
  `multi_device_scene`, `get_property` — all loop/group a single-item interface call per entry in
  Python rather than the interface itself being list-capable. Only `send_command`'s underlying
  interface (`send_commands`) is genuinely list-capable underneath. That distinction doesn't matter
  to the model (the tool call still looks the same either way), but it matters for how much work a
  similar fix is for the tools still listed as a gap above: no interface change needed, same
  handler-loop pattern these three already use.
- **`get_device_history` vs. `get_property` — same-looking problem, different right answer.**
  `get_device_history` broadcasts `device_ids` × `properties` as a real cross-product because it's
  a log *query* (`WHERE NodeAddress IN (...) AND ControlLabel IN (...)` is a legitimate single SQL
  statement). `get_property` reads live current values per device — there's no equivalent bulk
  fetch, and the real request shape is almost always exact pairs, not a matrix — so it followed
  `send_command`'s explicit-tuple-list shape instead. Worth remembering before reflexively copying
  `get_device_history`'s pattern onto the next tool.
- **`create_or_update_routine`** is categorically different — one call authors one whole DSL
  program. Batching several distinct routines' authoring into one call would mix multiple unrelated
  compile-failure paths in one response; not a small extension of the same pattern.
- **Pattern to not mistake for multi-target batching**: `send_command`'s `values`, `call_plugin`'s
  `args` — both are one call's own internal parameter container, not an array of separate targets.
